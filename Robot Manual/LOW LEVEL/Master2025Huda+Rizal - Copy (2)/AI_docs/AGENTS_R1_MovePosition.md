# AGENTS.md

Project: **R1 Move Position** — STM32F407 + FreeRTOS firmware for Robot R1, ABU Robocon 2026 “Kung Fu Quest”.

This file is the working contract for Codex/AI coding agents in this repository. The firmware controls real robot actuators, so every edit must be small, traceable, reviewable, and safe to test on hardware.

---

## 0. Current direction of the project

The old automatic `R1PathPlanner` approach is being phased out for Meihua Forest tuning. The new direction is a **manual 18-point Meihua Forest control mode**:

- The operator manually controls when R1 enters the Meihua point mode.
- R1 moves with blocking motion functions to one of 18 manually tuned Meihua pathway points.
- Heading is limited to 90-degree steps: `0`, `90`, `180`, `-90`.
- Point coordinates are tuned manually by the user, not generated by a planner.
- The 18 points must be ordered as a safe loop on the R1 Pathway, so moving `1 -> 2 -> ... -> 18 -> 1` stays safe.
- Do **not** implement new autonomous planner logic unless explicitly requested.

Important rule context:

- R1 may operate in Martial Club, Meihua Forest **R1 Pathway**, and Arena.
- R1 must not enter the green Forest/block area.
- R1 must not move R2 KFS or Fake KFS.
- Code changes around Meihua must preserve those constraints.

## 1. Operating rules for Codex

Work carefully. This repository controls motors, actuators, pneumatic/servo mechanisms, and robot motion.

### General rules

- Inspect the current code before editing.
- Read `AI_docs/` before touching movement code.
- Make one subsystem patch at a time.
- Prefer minimal diffs over full-file rewrites.
- Do not rewrite unrelated files.
- Do not remove or damage `USER CODE BEGIN` / `USER CODE END` regions.
- Do not assume actuator mapping, wheel IDs, encoder direction, joystick button names, or UART packet formats.
- If hardware behavior is unclear, stop and ask instead of guessing.
- Explain exactly which files changed and why.
- Keep old working functions unless the user explicitly asks to remove them.
- For new experimental low-level motion functions in `Swerve.c` / `Swerve.h`, use suffix `RIZAL`.
- Do not add continuous `printf` in real-time loops unless explicitly requested.

- Do not introduce blocking loops without `osDelay()` after FreeRTOS has started.
- Do not use `HAL_Delay()` in task-level motion/sequence code after the scheduler starts.
- Do not call expensive print/debug code from 1 ms odometry or motor loops.

### Build and test rules

- Do **not** run STM32CubeIDE headless builds, `make`, compiler, linker, or equivalent build commands from Codex.
- The user performs builds manually from STM32CubeIDE and pastes build logs for analysis.
- Codex may run non-build text checks such as `rg`, `grep`, `git diff`, and file inspection.
- Codex may run formatting-free static reasoning, but must not claim compile/build success unless the user-provided STM32CubeIDE log explicitly reports success.
- If a patch may require `.cproject`, `.project`, or Cube-generated metadata changes, explain that clearly instead of guessing.

### `R1MeihuaManual` should own 18-point manual mode data/state

The manual Meihua module should contain:

- `R1_MF_POINT_COUNT = 18`.
- `R1_MF_PointTable[18]` with tuneable coordinates.
- State variables:
  - current point `1..18`.
  - current heading index or heading deg.
  - saved exit point.
  - saved exit heading.
  - saved-exit valid flag.
- Helpers:
  - normalize / index heading in 90-degree steps.
  - next point with wrap `18 -> 1`.
  - previous point with wrap `1 -> 18`.
  - go to point blocking.
  - rotate left/right 90 deg.
  - save exit state.
  - return to saved point.

Do **not** put `SEQ_WAIT_RELEASE_WITH_BODY()` inside the new library yet. Keep button release/wait and sequence ordering in `main.c` until explicitly requested.

The library may expose action functions such as:

```c

void R1_MF_EnterPointMode(uint8_t start_point, float start_heading_deg);
void R1_MF_GoToPointBlocking(uint8_t point, float heading_deg, const R1MotionProfile_t* profile);
void R1_MF_GoNextPointBlocking(void);
void R1_MF_GoPrevPointBlocking(void);
void R1_MF_RotateLeft90Blocking(void);
void R1_MF_RotateRight90Blocking(void);
void R1_MF_SaveExitState(void);
uint8_t R1_MF_ReturnToSavedPointBlocking(void);
uint8_t R1_MF_GetCurrentPoint(void);
float R1_MF_GetCurrentHeading(void);
```

Button mapping stays in `main.c` for now:

```text
PS_CROSS / X     -> enter point mode and go to point 1
JOYS_L_KANAN     -> next point: 1 -> 2 -> ... -> 18 -> 1
JOYS_L_KIRI      -> previous point: 1 -> 18 -> ... -> 2 -> 1
L1               -> rotate left 90 deg
R1               -> rotate right 90 deg
JOYS_L_BAWAH     -> exit point mode and save current point/heading
JOYS_L_ATAS      -> return to saved point/heading
```

Heading convention:

```text
0 deg    = +Y world / forward from start
90 deg   = +X world / right
-90 deg  = -X world / left
180 deg  = -Y world / back
```

Use heading index if possible instead of accumulating floating error.

If final 18 coordinates are not present in the repository, do not invent field-critical values. Create a compile-valid table with explicit `TODO_TUNE` comments and avoid auto-running it in sequence until the user fills the coordinates.

## 7. Manual 18-point behavior requirements

The new 18-point mode is allowed to use blocking motion functions because `JalanKeTitikRIZAL()` and related movement loops call `osDelay(5)` internally and are RTOS-friendly.

Expected behavior:

1. Operator is in manual control.
2. After staff/weapon assembly, operator presses `X`.
3. R1 enters blocking Meihua point mode and goes to point 1.
4. Inside the mode:
   - `JOYS_L_KANAN`: go to next point.
   - `JOYS_L_KIRI`: go to previous point.
   - `L1`: rotate left 90 deg.
   - `R1`: rotate right 90 deg.
   - `JOYS_L_BAWAH`: save current point/heading and exit to normal manual control.
5. From outside mode:
   - `JOYS_L_ATAS`: return to saved point and saved heading, then re-enter point mode.

Important safety property:

- The mode must not decide a new route automatically.
- It only goes to the next/previous point selected by the operator.
- The safety of straight-line motion between neighboring points depends on the manually tuned 18-point loop.

## 8. Motion tuning rules

For movement wrappers:

- Prefer profile-based functions.
- Do not hardcode PID values in many places.
- Tune through `R1MotionProfile_t` presets.
- Keep default wrappers for compatibility.
- If using dynamic brake, call it explicitly after movement wrapper, not inside `RodaStop()`.

Motion profile fields meaning:

- `max_output_speed`: maximum output speed.
- `start_output_speed`: start speed passed to the low-level movement function.
- `arrive_distance_mm`: distance tolerance for arriving.
- `arrive_heading_deg`: heading tolerance for arriving.
- `pid_distance_limit_mm`: clamp distance error before PID.
- `pid_heading_limit_deg`: clamp heading error before PID; indirectly limits heading speed.
- `kp_distance`, `kd_distance`: distance response/damping.
- `kp_heading`, `kd_heading`: heading response/damping.

Do not tune by changing `Kinematik()`.

## 9. Odometry and world position rules

- Do not change `PosX_World`, `PosY_World`, or `RobotYaw` semantics to compensate for mechanism offsets.
- Do not change deadwheel geometry unless explicitly requested.
- If a different physical reference point is needed, use a target conversion wrapper, not odometry changes.
- Current coordinate convention:
  - body `X+` = right robot.
  - body `Y+` = front robot.
  - world `X+` = right field.
  - world `Y+` = forward from start.
  - yaw `0` = world `Y+`.
  - yaw `90` = world `X+`.
